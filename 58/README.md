## 내용정리

> `dev-practice-commerce_v1.1` 프로젝트(`core/core-api`, `storage/db-core`)에 남겨둔 주석 정리

### 공통

인증 (`UserArgumentResolver`)

- 이 서버는 G/W 뒤쪽 Internal Network 에 있다고 가정한다.
- 유저 인증은 G/W 에서 처리하고, 서버에는 `userId` 만 넘어온다고 가정한다.

서비스 구현 패턴 (`ProductService`)

- 서비스를 구현하는 방식은 여러 가지다. 컴포넌트로 나누거나, 코드를 서비스 안에 다 풀어두거나.
- 강사가 가장 선호하는 형태
  - 서비스 안에서는 비즈니스 플로우가 보이게 한다.
  - 그 안에서는 행위 기준으로 이름을 지은 컴포넌트(`ProductFinder`, `ReviewManager`, `ReviewPolicyValidator` 등)를 사용한다.
- 로직이 있는 경우(리뷰 추가/수정 등) 응집된 컴포넌트로 묶으면 좋은 점 (`ReviewService`)
  - 단위 테스트하기 좋다.
  - 트랜잭션을 묶기 좋다.
  - 서비스 영역의 코드를 읽기 쉬워진다.
- CRUD 가 단순하면 컴포넌트로 나누지 않아도 괜찮다. (`QnAService`)
  - 다만 소프트웨어가 커질수록 코드 형태가 곳곳마다 다르면 새로 온 사람이 파악하기 어렵다. → 일관된 형태가 좋다.

컨트롤러의 역할 (`ProductController`)

- 컨트롤러는 클라이언트에 맞게 여러 서비스의 데이터를 조합하거나 가공해서 내려주기도 한다.

엔티티와 개념 클래스 분리 (`ProductEntity`)

- 개념 클래스 `Product` 는 가격 필드를 `Price` 로 묶었지만, `ProductEntity` 에서는 임베디드 타입을 쓰지 않고 필드를 플랫하게 둔다.
  - 엔티티와 개념 클래스를 분리하는 쪽을 선호해서 이렇게 설계했다.
  - 엔티티를 개념 클래스로 그대로 쓰는 방법도 있다.
- `Price` 는 지금은 필드만 있지만, 실무에서는 금액 계산 로직이 들어갈 수 있으니 묶어두는 게 좋다. (`Price`)

hard-delete 를 잘 하지 않는다 (`FavoriteService`)

- 서비스 개발에서는 데이터를 실제로 지우는 경우가 드물다. `EntityStatus` 로 상태만 바꾼다.
- 데이터를 지우면 추적하거나 분석하기 어렵다.

### 상품

카테고리 조회와 삭제 규칙 (`ProductFinder`)

- 모든 테이블에 `EntityStatus` 가 있는데, 카테고리별 상품 조회에서 `ProductCategoryEntity` 는 `ACTIVE` 조건으로 조회하고 `ProductEntity` 는 조건 없이 조회한다.
  - 카테고리에 속한 상품은 삭제될 수 없다고 정의했기 때문이다.
  - 상품을 삭제하려면 연결된 `ProductCategory` 가 모두 지워져 있어야 한다.
- `Product`, `ProductCategory` 모두 삭제 여부를 체크할 수도 있지만 번거롭다.
- 구현 방법 (여기서는 1번을 사용)
  1. `ProductCategory` 가 1개라도 있으면 상품을 삭제하지 못하게 한다.
  2. 상품을 삭제할 때 연결된 `ProductCategory` 를 모두 삭제한다.
  3. 그 밖에도 여러 방법이 있을 수 있다.

네이밍 (`ProductCategoryEntity`)

- 카테고리 안에 상품이 있으니 `CategoryProductEntity` 라고 생각할 수도 있다.
- 하지만 카테고리가 부수적인 개념이라고 봐서 `ProductCategoryEntity` 로 이름 지었다.

상품 섹션 (`ProductSection`, `ProductSectionService`)

- 상품 상세에서는 여러 정보를 동적으로 만들어 보여주고 싶을 수 있다. → `ProductSection(type, content)` 목록으로 표현
- `ProductService` 와 분리한 이유: `ProductSection` 은 상품 상세에서만 쓰이지만 `Product` 는 여러 곳에서 쓰인다.

상품 상세 API 에서 평점을 조합하는 이유 (`ProductController.findProduct`)

- 상품 상세 API 는 상품, 섹션, 리뷰 평점 요약, 쿠폰을 컨트롤러에서 조합해서 응답한다.
- 평점도 상품 서비스에 넣으면 어떨까?
  - 그러면 상품 서비스가 리뷰를 알게 된다.
  - 상품과 리뷰는 개념이 달라서 격벽이 있는데, 상품 → 리뷰 의존이 생긴다.
  - 지금 상품은 리뷰를 모르고, 알 필요도 없다.
- 쿠폰 목록도 함께 내려주고 있는데, 별도 API 로 분리하는 게 나을지는 고민거리로 남겨둠.

### 리뷰

리뷰 대상 확장 (`ReviewController`, `ReviewEntity`)

- 리뷰는 앞으로 확장될 수 있다는 요구사항이 있다.
  - 지금은 상품에만 달 수 있지만, 나중에는 판매자, 상품 옵션 등 상품이 아닌 대상에도 달 수 있다.
  - 그래서 `ReviewTarget(type, id)` 로 리뷰 대상을 추상화했다.
- 리뷰키(`reviewKey`)는 대상과 상관없이 리뷰를 쓸 수 있게 하려고 사용한다.
  - 상품 리뷰라면 `ORDER_ITEM_{주문아이템ID}` 형태이고, `(userId, reviewKey)` 유니크 인덱스로 주문 아이템 하나에 리뷰 하나만 쓰게 한다.

리뷰 정책 (`ReviewPolicyValidator`)

- 최근 14일 안에 주문(`PAID`) 이력이 있어야 리뷰를 쓸 수 있다.
- 리뷰는 작성 후 7일 안에만 수정할 수 있다.

리뷰 히스토리 (`ReviewManager`)

- 지금은 단순히 저장만 하지만, 리뷰는 분쟁 요소가 많다. → 대응하려면 수정 히스토리가 필요하다.
- 아직은 그런 요구사항이 없는 상황이다.

### QnA

- QnA 는 아예 상품 전용으로 지정했다. (`QuestionEntity.productId`)
- 답변 API 가 없는 이유: 서비스 API 이므로 답변은 어드민 기능으로 보고 이 코드에서는 뺐다. (`QnAController`, `QnAService`)
- `Answer.EMPTY` (`id = -1`) 는 답변이 없는 상태를 뜻한다고 협의한 것이다. (`Answer`)

### 찜

찜하기/찜해제 API (`FavoriteController`)

- 찜 API 하나로 토글 방식으로 처리하면 따닥(더블 클릭) 문제가 생길 수 있다.
- 이를 막으려고 찜하기/찜해제를 분리했다. 여기서는 요청의 `type`(`FAVORITE`, `UNFAVORITE`)으로 구분한다.

30일 이내 찜만 유지 (`FavoriteService`)

- 30일 이내의 찜만 보여준다는 스펙이다. 조회할 때 `updatedAt` 이 30일 이내인 것만 가져온다.
- 배치 등으로 오래된 찜을 실제로 지우지는 않는다.
  - 데이터가 많이 쌓이지 않고, 복잡도를 고려한 선택이다. 나중에 분석용으로 쓸 수도 있다.
  - 큰 시스템이라면 분석용으로 데이터를 따로 동기화해두겠지만..

### 쿠폰

쿠폰 다운로드 (`CouponService.download`)

- 지금은 다운로드가 매우 단순하게 구현되어 있어서 서비스 측면에서는 아쉽다.
- 이미 다운로드한 쿠폰인지 알 수 있는 방법이 없다. (다시 다운로드를 시도해야 `COUPON_ALREADY_DOWNLOADED` 에러로 알 수 있음)

쿠폰 정보 변경 시 영향 (`OwnedCouponService`)

- 소유 쿠폰은 `couponId` 만 가지고 있고, 조회할 때 쿠폰 정보를 가져와서 조합한다.
- 그래서 운영팀이 쿠폰의 할인 금액이나 만료일을 바꾸면 이미 발급된 쿠폰에도 모두 적용된다.
  - 장점일 수도 단점일 수도 있다. → 기획 요구사항에 따라 달라진다.
  - 쿠폰 정보가 바뀌어도 이미 다운로드한 사람에게는 영향이 없게 하려면 소유 쿠폰에 스냅샷을 저장해야 한다.

### 포인트

- 포인트 적립/사용은 비즈니스 플로우(결제, 리뷰 등) 안에서 호출되므로, 컨트롤러에는 포인트 조회만 있다. (`PointController`)
- 지금은 최종 포인트 잔액만 보여주는 요구사항이다. 포인트를 건별로 관리하지 않는다. (`PointService`)
  - 건별 관리가 정말 필요한지 고민해보고, 그런 요구사항이 오면 간단하게 가자고 역제안해볼 수도 있다.
- 모든 유저는 가입할 때 포인트 잔액(`point_balance`) 데이터를 만든다고 가정한다. (`PointHandler`)
  - 이렇게 하면 서비스 로직이 단순해진다. 그렇지 않으면 잔액 데이터가 있는지에 따른 분기 로직이 많이 필요할 수 있다.
- 포인트는 재화라서 동시 수정 충돌을 막으려고 `@Version` 칼럼으로 낙관적 락을 건다. (`PointBalanceEntity`)

### 장바구니

- 장바구니(카트)는 하나이고, 카트 안에 들어가는 것을 아이템이라고 정의했다. API 도 `/v1/cart` 조회, `/v1/cart/items` 추가/수정/삭제로 나뉜다. (`CartController`)
- `Cart` 라는 엔티티는 없다. 클래스로만 존재하는 논리적인 개념이다. 유저의 `CartItemEntity` 들을 모아서 `Cart` 를 만든다. (`CartService`)

### 주문

주문 생성 흐름 (`OrderController`)

- 상품 바로 주문(`create`)과 장바구니 주문(`createFromCart`) 모두 `orderService.create()` 를 호출한다. → 입력을 `NewOrder` 로 맞춰주면 뒷단은 똑같이 처리된다.

주문 키 (`OrderService`)

- 주문은 auto increment ID 를 외부에 노출하지 않고, 별도 키 생성기(`OrderKeyGenerator`)로 만든 `orderKey` 를 쓴다.
  - 보안상 이유
  - 순차 ID 를 노출하면 경쟁사가 주문 건수를 추정할 수 있다.
  - `OrderKeyGenerator.generate()`(UUID → Base64 URL 인코딩)는 임의로 만든 구현이라 참고만 하면 된다.

주문 데이터 생성 시점 (`OrderService`)

- 주문 데이터는 주문을 만드는 시점(결제 전, `CREATED` 상태)에 생성하는 것이 좋다.
  - 안정적으로 다룰 수 있고 운영하기 편하다.
  - 주문은 중요한 역할을 한다.
  - 다만 중간에 이탈하면 쓰레기 데이터가 생길 수 있다.

### 결제

PG 콜백 (`PaymentController`)

- 결제 성공/실패 콜백은 PG 사가 호출하는 엔드포인트다.
- PG 사가 호출하므로 `RequestParam` 은 PG 사의 스펙을 따른다.
- 결제 수단(`PaymentMethod`), 승인 번호, 결제 시각 등은 PG 사 응답으로 채워지는 값이다. (`PaymentEntity`)

결제 성공 처리 (`PaymentService.success`)

- PG 승인 API 를 호출해서 성공하면 다음 로직으로 넘어가고, 실패하면 예외를 던진다.
- 승인 API 호출 이후로는 실제로 결제된 상태이므로 가급적 예외가 나면 안 된다.
  - 결제/주문 상태 변경, 쿠폰 사용, 포인트 차감/적립, 거래 이력 저장을 트랜잭션으로 묶는다.
  - 어디서 실패하더라도 로깅만 하고 넘어가는 게 나을 수도 있다.

결제 실패 처리 (`PaymentService.fail`)

- 주문 상태도, 결제 상태도 바꾸지 않는다. `TransactionHistory` 에 실패 기록만 남긴다.
  - 결제가 성공할 때까지 같은 주문을 다시 쓸 수 있다.
  - 결제 데이터는 새로 생성될 수 있다.
- 기획에서 결제 실패 상태를 알고 싶어 할 수 있다. (결제가 실패한 건지, 주문창을 그냥 닫은 건지 등)
  - 따로 적재한 데이터로 확인할 수 있다면, 거래 이력 등으로 결제 실패 여부는 알 수 있다.
- 상태를 다루는 일은 운영을 귀찮고 복잡하게 만든다. 상태를 최소화하는 게 운영과 확장에 도움이 된다.
  - 상태는 문제를 많이 일으킬 수 있다.

### 취소

`CancelService`

- PG 취소 API 를 호출해서 성공하면 다음 로직으로 넘어가고, 실패하면 예외를 던진다.
- 취소를 결제와 분리하는 쪽을 선호한다.
  - 결제에 취소 상태를 두고 결제 하나로 모두 다룰 수도 있다. 하지만 그러면 `Payment` 가 결제뿐 아니라 취소 때도 수정된다.
  - 무조건 정답이라고 할 수는 없지만, 이 선택은 정산 쪽에 유리하다.
- 결제와 취소를 각각의 테이블에 저장하고 Immutable 하게 관리한다.
  - 저장만 하므로 수정 이력을 확인할 필요가 없다.
- 단점: 데이터가 흩어져 있어서 화면을 그릴 때 조금 더 불편할 수 있다. → 트레이드오프를 고민해야 한다.
- 취소가 많이 생길까? → 일반적인 운영 상황에서 취소는 많지 않다.

### 정산

배치 구성 (`SettlementBatchController`)

- 스프링 배치 등은 쓰지 않는다. 데이터가 많지 않다.
- 크론잡으로 내부 배치 API(`/internal-batch/...`)를 호출한다.
- 큰 작업을 작은 작업 여러 개로 나누어 처리한다.
  - 정산 대상 적재 (오전 1시): 어제 00:00:00 ~ 23:59:59 의 결제/취소 건을 정산 대상으로 적재
  - 정산 계산 (오전 4시): 정산 대상을 가맹점별로 집계하고 수수료를 뺀 정산금 계산
  - 정산 입금 (오전 9시): `READY` 상태의 정산금을 가맹점에 이체
- 작업을 시간 기준으로 나눈다.
  - 작업이 커져서 다음 시간대 배치가 시작되기 전에 이전 배치가 끝나지 않으면 다음 배치가 제대로 동작하지 않을 수 있다.
  - 데이터가 적을 때는 충분히 쓸 만한 전략이다.
- 배치를 나누어 두면 테스트하기 쉽다. (`SettlementService`)

정산 입금 (`SettlementService.transfer`)

- 가맹점별 총 정산금이 0 이하(음수)라면 보낼 돈이 없으므로, 정산금이 양수가 될 때까지 건너뛴다. (경고 로그만 남김)
- 실제로는 이 부분에서 외부 펌뱅킹 등 이체 서비스 API 를 호출한다.
